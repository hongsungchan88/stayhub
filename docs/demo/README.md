# 전시회 시연용 데모 데이터

12/1~3 시제품 전시회에서 노트북으로 시연할 때 쓰는 데이터입니다.
`demo-data.sql` 은 **앱이 자동으로 넣지 않습니다.** 필요할 때 손으로 한 번 실행합니다.

## 실행 방법

1. **앱을 먼저 한 번 켭니다.** 테이블(ddl-auto)과 기본 데이터(`data.sql`의 시설 코드·채널 1·2번)가 있어야 합니다.
2. 아래 둘 중 하나로 `docs/demo/demo-data.sql` 을 실행합니다.
   - **MySQL 명령줄**
     ```
     mysql -u root -p --default-character-set=utf8mb4 stayhub
     mysql> source C:/경로/stayhub/docs/demo/demo-data.sql
     ```
   - **IntelliJ** — Database 창에서 stayhub 데이터소스를 연결한 뒤, 파일을 열고 전체 선택 → 실행(Ctrl+Enter).
3. 마지막에 나오는 세 결과로 확인합니다.
   - **겹침 확인**: 0행이어야 정상 (같은 객실에서 날짜가 겹치는 예약이 없음)
   - **입실 기록 확인**: 0행이어야 정상 (투숙 중인데 입실 기록이 없는 예약이 없음)
   - **건수**: 아래 표와 같으면 정상
4. 앱이 켜져 있었다면 화면만 새로고침하면 됩니다(재시작 필요 없음).

**12/1 아침에 한 번 더 실행하면 날짜가 그날 기준으로 다시 맞춰집니다.** 날짜가 전부 `CURDATE()`/`NOW()` 기준 상대값이라서,
"오늘 체크인 3건", "오늘 체크아웃 2건", "오늘 청소 5건" 이 실행한 날 기준으로 다시 만들어집니다. 2·3일 차 아침에도 똑같이 실행하세요.

### 여러 번 실행해도 되나요?

됩니다. 데모 행은 ID **900001~900999** 로 고정이고, 파일 맨 앞에서 그 범위만 지운 뒤 다시 넣습니다. 그 밖의 데이터는 건드리지 않습니다.

- 숙소 1번은 지우지 않고 이름·소개·상태만 UPDATE 합니다(없으면 새로 만듭니다). 시설 연결(주차·와이파이·조식)은 없을 때만 추가합니다.
- 데모 데이터를 넣고 나면 테이블의 자동 번호가 900051 처럼 이어집니다. 그래서 **시연 중에 화면에서 새로 만든 예약·결제 등도
  ID가 900xxx 범위라, 다시 실행하면 함께 지워집니다.** (시연 상태를 처음으로 되돌리는 용도로 쓰면 됩니다)
- 자동 번호가 900xxx 가 아닌 기록(입실 기록·채널 연결·객실 상태 기록·일별 요금·세금계산서)은 데모 예약·객실·결제 번호로 찾아 지웁니다.
  모의 채널 A 가져오기 기록은 전부 지웁니다. 그래서 다시 실행하면 **같은 채널 예약(A-1001 등)을 다시 가져올 수 있습니다.**
- 객실 번호(201~505)가 이미 다른 객실에 쓰이고 있으면 `room_number` 중복으로 실패합니다. 이때는 트랜잭션이라 아무것도 바뀌지 않습니다.

## 시연 계정

비밀번호는 모두 **`Demo1234!`** 입니다.

| 아이디 | 역할 | 이름 | 주로 보여 줄 화면 |
|---|---|---|---|
| `demo_host` | HOST | 시연 호스트 | 대시보드, 예약 목록, 결제·환불, 채널 수수료, 소개페이지 |
| `demo_front` | FRONT | 시연 프런트 | 예약 목록, 체크인/체크아웃, 특별 요청, 추가 요금, 통합 인박스 |
| `demo_staff` | STAFF | 시연 직원 | 대시보드만 (다른 메뉴는 403) |
| `demo_cleaning` | CLEANING | 시연 청소 | 객실 현황 보드, 청소 스케줄 (예약·결제는 403) |

- 오늘 체크인 예정(예약 확정): **201 · 302 · 403호**
- 오늘 체크아웃 예정(투숙 중): **202 · 303호**
- 투숙 중 7곳 중 **미정산 추가 요금이 있어 체크아웃이 막히는 객실: 202 · 203 · 304호**
  (202 레이트 체크아웃 2만 원, 203 미니바 1.5만 원, 304 얼리 체크인 3만 원). **바로 체크아웃되는 객실: 205 · 303 · 402 · 502호**

- 결제 수단: 채널 예약은 **사전 결제**(예약할 때), 채널 없는 게스트 직접 예약은 **현장 결제**(체크인할 때)입니다.
  그래서 체크인 전인 게스트 직접 예약 2건은 아직 결제가 없습니다. 현장 결제는 1번 "직접 예약" 채널로 넣었습니다(결제의 channel_id 는 비울 수 없음).
- 결제 수수료·실매출은 PaymentService 와 같은 방식(등록 채널은 수수료율, 미등록은 기본 수수료율, 소수 둘째 자리 반올림)으로
  `channels` 테이블 값을 읽어 계산합니다. 수수료율을 바꾼 뒤 다시 실행하면 새 율로 계산됩니다.
- 통계(`/api/statistics/occupancy · channels · revenue`)는 최근 30일 기준으로 숫자가 나옵니다.

## 시연 추천 순서

1. **게스트 예약** (로그인 없이) — `/` 숙소 소개 → `/guidebook` → `/reserve` 에서 날짜·인원으로 빈 객실 찾기 → 예약.
   이미 예약된 객실은 목록에 안 나오고, 취소된 예약의 객실은 다시 나오는 것을 보여 줍니다.
2. **관리자 예약 목록** (`demo_host`) — `/admin/reservations` 에서 방금 만든 게스트 예약 확인, 이름·채널로 검색.
3. **프런트 체크인** (`demo_front`) — `/admin/check-in-out` 에서 오늘 체크인 예정 201·302·403호 체크인.
   - **바로 체크아웃**: 303호(오늘 퇴실) 체크아웃 → 객실이 "청소 필요"로 바뀌고 청소 작업이 생깁니다. 205·402·502호도 됩니다.
   - **미정산 차단**: 202호(오늘 퇴실) 체크아웃 → "정산되지 않은 추가 요금이 있어 체크아웃할 수 없습니다." 문구.
     `/admin/additional-charges` 에서 그 요금을 정산 처리한 뒤 다시 누르면 체크아웃됩니다. 203·304호도 같은 차단입니다.
   302호는 특별 요청(아기 침대)과 인박스 문의가 같이 걸려 있어 이야기를 이어 가기 좋습니다.
4. **청소** (`demo_cleaning`) — `/admin/housekeeping-tasks` 에서 204·305호 청소 시작 → 완료, `/admin/rooms` 에서 객실 상태 변화.
5. **결제·통계** (`demo_host`) — `/admin/payments` 결제·환불 내역(전액·부분 환불 각 1건), `/admin/channel-commissions` 수수료율,
   통계 API 최근 30일 가동률·채널별 예약·매출.
6. **인박스** (`demo_front`) — `/admin/messages` 에서 "수동 응대 필요" 스레드에 답장.
7. **권한(403)** — `demo_staff` 로 `/admin/payments`, `demo_cleaning` 으로 `/admin/reservations` 를 열면 403 화면.

> 11/23 main 기준으로 대시보드(`/admin`)와 체크인/체크아웃(`/admin/check-in-out`) 화면은 아직 "준비 중" 입니다.
> 데이터는 미리 들어가 있으니 화면이 완성되면 위 순서 그대로 쓰면 됩니다.
